## 1. Retrieval

26 questions have known relevant documents. Each was run through three retrievers and scored on the top 6 chunks.

| Retriever | Hit rate | Recall | Context precision | MRR |
|---|---|---|---|---|
| Vector only | 100.0% | 96.5% | 39.1% | 0.946 |
| BM25 only | 88.5% | 85.9% | 34.6% | 0.777 |
| Hybrid (RRF + metadata filters) | 100.0% | 97.4% | 44.9% | 0.926 |

How to read this:
- **Hit rate**: at least one relevant chunk in the top k. **Recall**: share of the relevant documents found.
- **Context precision**: share of retrieved chunks that belong to a relevant document. Most questions have one relevant document with one or two chunks, so the ceiling is far below 100%.
- **MRR**: how high the first relevant chunk ranks (1.0 means always first).

Retrieval latency (embedding + vector search + BM25 + fusion, local CPU): p50 7.7 ms, p95 9.8 ms.

## 5. Failure handling

LLM and API failures are covered by automated tests rather than by this script, because they need a controllable fake provider (`tests/test_llm_and_guardrails.py`, `tests/test_api.py`): rate limit then fallback to the next model, removed model, timeout, empty completion, HTTP 200 with an error body, invalid key, and the whole chain down (the API still returns 200 with retrieved passages).

## 6. Limits of this evaluation

- The test set is small and was written by the same person who built the system, so it measures regressions well and absolute quality only roughly.
- Wasalt coverage is 21 listings from one Riyadh district (see the README for why), so Wasalt questions are less varied than they would be with a full crawl.
- Relevance labels are per document, not per chunk.
